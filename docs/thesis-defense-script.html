Attack Vector Classifier — 16-Type Taxonomy

Keyword-based classification · Maps free-text exploit descriptions to AttackVector enum
🎤 You Say

"When raw exploit data arrives from DefiLlama, the technique field is free-text — 'Flash Loan Attack', 'Price Oracle Manipulation', etc. Our AttackVectorClassifier uses keyword matching with confidence scoring to map these descriptions to our 16-member AttackVector enum. This is critical because it enables structured querying and pattern analysis across the entire DeFi exploit landscape. Let me walk you through each attack vector and why it matters."

🔐
ACCESS_CONTROL Critical

Exploits that bypass authorization checks — compromised private keys, unprotected admin functions, or privilege escalation. The attacker gains unauthorized access to privileged operations like fund withdrawal, ownership transfer, or contract upgrades. This is the most common attack vector in DeFi, accounting for the largest cumulative losses.

access control private key admin privilege unauthorized
⚡
FLASH_LOAN Critical

Leverages uncollateralized loans that must be repaid within a single transaction. The attacker borrows millions, manipulates markets or exploits vulnerable contracts, profits, and repays — all atomically. Flash loans democratize exploit capital, meaning any attacker can execute multi-million dollar attacks with zero upfront funds.

flash loan flashloan flash-loan
📊
ORACLE_MANIPULATION Critical

Targets price feed mechanisms that DeFi protocols depend on for asset valuation. The attacker manipulates spot prices on a DEX (often via flash loans) to distort oracle readings, causing lending protocols to issue undercollateralized loans or triggering false liquidations. Exploits the gap between instantaneous spot price and true market value.

oracle price manipulation price oracle twap
🔄
REENTRANCY Critical

The classic smart contract vulnerability — an external call re-enters the calling contract before state updates complete. This allows an attacker to repeatedly withdraw funds before the balance is decremented. The 2016 DAO hack ($60M) was a reentrancy exploit. Despite being well-known, new variants (cross-function, cross-contract, read-only) continue to emerge.

reentrancy re-entrancy reentrant
🎣
PHISHING High

Social engineering attacks that trick users or developers into signing malicious transactions, approving token drains, or revealing private keys. Includes fake dApp frontends, malicious token approvals, and targeted spear-phishing of protocol team members. Often the entry point for access control compromises — the private key wasn't hacked, it was stolen.

phishing social engineering fake
🏃
RUG_PULL Critical

Insider fraud where the protocol creators intentionally drain liquidity or user funds. Typically involves deploying a token with hidden backdoors (mint functions, transfer restrictions), building hype to attract deposits, then executing a premeditated exit — removing all liquidity or minting unlimited tokens to dump on investors.

rug pull rugpull exit scam
🏎️
FRONTRUNNING High

MEV (Maximal Extractable Value) attacks where bots monitor the mempool for profitable transactions and insert their own transactions before or around the victim's. Includes sandwich attacks (buy before, sell after a large swap), generalized frontrunning (copying profitable transactions), and JIT liquidity attacks.

frontrun sandwich mev front-run
🏛️
DAO_GOVERNANCE Medium

Exploits the on-chain governance mechanisms of DAOs. The attacker acquires enough voting power (often via flash loans) to pass malicious proposals — draining treasuries, changing protocol parameters, or upgrading contracts to attacker-controlled code. Targets the democratic assumption that token holders act in the protocol's interest.

governance dao voting
🔢
ARITHMETIC_OVERFLOW High

Integer overflow/underflow vulnerabilities where arithmetic operations wrap around, producing unexpected values. A balance subtraction can underflow to a massive number, granting the attacker near-infinite tokens. While Solidity 0.8+ has built-in overflow checks, older contracts and unchecked blocks remain vulnerable.

overflow underflow integer
💉
DELEGATECALL_INJECTION Critical

Exploits the delegatecall opcode which executes external code in the caller's storage context. If a proxy contract's implementation address is writable, an attacker can redirect it to malicious code that operates on the proxy's storage — effectively hijacking the entire contract state, including all user funds.

delegatecall proxy call injection
🚫
DOS Medium

Denial of Service attacks that render a contract unusable. Includes gas griefing (making functions exceed block gas limits), blocking critical operations (e.g., always-reverting fallback functions in auction contracts), and state bloating that makes iteration over storage arrays impossible.

dos denial of service griefing
📼
REPLAY High

Reuses valid signatures or transactions in unintended contexts — across chains (post-fork replay), across contracts (missing domain separators), or repeated submissions (missing nonce checks). Particularly dangerous during chain forks and L2 deployments where the same signed message may be valid on multiple networks.

replay signature replay
💥
SELF_DESTRUCT Medium

Uses the selfdestruct opcode to forcibly send ETH to a target contract, bypassing its fallback/receive functions. This can break contracts that rely on address(this).balance for logic. Also used to destroy implementation contracts behind proxies, permanently bricking the protocol.

selfdestruct self-destruct suicide
🌉
BRIDGE_EXPLOIT Critical

Targets cross-chain bridge protocols — the most catastrophic attack vector in DeFi. Bridges hold massive TVL as collateral for wrapped assets. Exploits include forging deposit proofs, compromising validator/relayer keys, or exploiting message verification logic. The Ronin ($625M), Wormhole ($326M), and Nomad ($190M) hacks were all bridge exploits.

bridge cross-chain cross chain
🐛
LOGIC_ERROR High

Catch-all for implementation bugs that don't fit other categories — incorrect conditional logic, wrong variable usage, missing edge case handling, or flawed business logic. These are protocol-specific vulnerabilities that require deep understanding of the contract's intended behavior to identify and exploit.

logic bug implementation error
🎤 You Say

"These 16 attack vectors represent the complete taxonomy of how DeFi protocols are exploited. Our classifier maps free-text descriptions to this enum using keyword matching — the grey tags you see on each card are the exact keywords the classifier scans for. 🟢 Moderate

Foundational Understanding (Q1–Q5)

Q1 "Why did you choose Hexagonal Architecture over Clean Architecture or traditional layered MVC?" ▼

Both Hexagonal and Clean Architecture share dependency inversion. We chose Hexagonal for three reasons:

  1. Simplicity — Hexagonal uses a two-concept model (ports + adapters) vs. Clean Architecture's multiple concentric rings. Less cognitive overhead for a thesis project.
  2. Explicit integration surfaces — Every interaction is mediated by a named port interface. The system's contracts are self-documenting.
  3. Testability — Each port can have multiple adapters (production PostgreSQL + test in-memory). ADR-001 documents this decision.
Q2 "Can you explain the difference between a driving adapter and a driven adapter in your system?" ▼

The distinction maps to direction of control flow:

A driving adapter (inbound) initiates requests into our domain — e.g., Fastify HTTP handlers and BullMQ Workers. They call into use cases.

A driven adapter (outbound) is called by our domain through a port interface — e.g., PostgresHackDataAdapter, RedisCacheAdapter, DefiLlamaAdapter.

Key insight: driving adapters depend on use cases, while use cases depend on port interfaces — not driven adapters directly. Driven adapters are injected at composition time. This is the Dependency Inversion Principle in action.

Q3 "Why did you use Zod schemas for domain entities instead of traditional TypeScript classes?" ▼

Documented in ADR-008. Three benefits:

  1. Single source of truth — Zod schemas define both runtime validation and TypeScript types via z.infer. Zero duplication.
  2. Inherent serializability — Plain objects can be returned directly from APIs, stored in Redis, or logged without custom toJSON() methods.
  3. Immutability by convention — No setter methods. Domain logic uses factory functions that return new objects.
Q4 "What is the purpose of the SafetyLabel four-state lifecycle, and why not binary SAFE/MALICIOUS?" ▼

UNANALYZED is necessary because files are indexed asynchronously — they enter the system before being scanned.

The SUSPICIOUS state is the key design decision. Our AST scanner detects patterns like require('child_process') or fetch() to external URLs. These may indicate malicious intent but can't be conclusively classified without human review.

Binary classification would force either false positives (blocking legitimate files) or false negatives (allowing dangerous files). The three-tier model creates a triage queue — mirroring established malware classification in cybersecurity.

Q5 "How does your ETL pipeline handle deduplication of hack incidents?" ▼

Five-stage pipeline: Fetch → Normalize → Enrich → Deduplicate → Validate.

Deduplication at stage 4 uses a composite key: protocol name + incident date + chain. Matching records trigger an UPSERT — updating existing records with new information rather than creating duplicates.

Stage 5 (Validate) enforces schema invariants — e.g., fundsReturned ≤ lossUsd — ensuring data integrity even when external sources provide inconsistent data.

🟡 Advanced

Architecture Trade-offs & Technical Depth (Q6–Q10)

Q6 "Your system uses both Viem and ethers.js. Isn't that redundant?" ▼

Addressed in ADR-007. Viem is our primary choice for type-safe chain interactions. ethers.js v6 is retained for mature ABI encoding and broader Foundry ecosystem compatibility.

The critical point: both libraries are hidden behind the IChainDataPort interface. The domain core never knows which library makes the RPC call. The EvmRpcAdapter internally uses whichever is most appropriate per method. This is the exact benefit of Ports and Adapters — infrastructure heterogeneity is isolated from domain logic.

Q7 "How does the Acorn AST safety scanner work, and what are its limitations vs. LLM-based approaches?" ▼

Four stages: AST parsing → Rule engine evaluation → Severity scoring → Label assignment.

The rule engine walks the AST for: CallExpression nodes targeting eval(), exec(); ImportDeclaration nodes importing fs/net modules; string literals matching prompt injection or exfiltration patterns.

Limitation: Acorn is syntactic — it cannot understand semantic intent. A fetch('https://api.etherscan.io/...') could be legitimate or exfiltration.

Why Acorn (ADR-009): deterministic, tiny footprint (<200KB), and no false confidence — SUSPICIOUS honestly communicates uncertainty. The ISafetyScannerPort supports future migration to LLM-based or hybrid scanners without domain changes.

Q8 "How do you ensure type safety across three engines sharing domain types through @aegis/core?" ▼

Type safety enforced at four levels:

  1. Compile-time — TypeScript project references with composite builds. Turborepo ensures topological build ordering.
  2. Runtime boundary validation — Zod schemas at every API boundary. z.infer generates types directly from schemas.
  3. Port contracts — Port interfaces in @aegis/core. Any adapter must satisfy the full interface or produce compile errors.
  4. Strict TypeScript — noUncheckedIndexedAccess, exactOptionalPropertyTypes, noImplicitAny.
Q9 "How does the FoundryRunner handle process failures, timeouts, and resource limits?" ▼

The FoundryRunner adapter manages Foundry as a controlled subprocess with:

  • Timeouts — configurable max execution time; kills process and returns structured error
  • Gas limits — ForkParameters schema includes gasLimit to constrain simulation
  • Output streaming — ISimulationPort streams stdout/stderr for real-time progress
  • Structured errors — Failures mapped to AegisError hierarchy (ExternalServiceError 502, ValidationError 400)
  • Isolation — Each simulation runs its own process with own fork state; no cross-contamination
Q10 "How does your caching strategy handle invalidation during ETL syncs?" ▼

TTL-based expiration with event-driven invalidation:

  • Hack list queries: 60s TTL | Hack detail/stats: 300s TTL
  • Short TTL for lists = near-real-time; longer TTL for details = less frequent changes

During ETL sync, after database UPSERT, the pipeline explicitly invalidates affected caches — pattern-based deletion on aegis:hacks:list:* and dashboard stats. Users see fresh data immediately after sync.

🔴 High-Level

Strategic & Research-Level (Q11–Q16)

Q11 "Doesn't your shared kernel risk becoming a 'god module' that breaks all engines when changed?" ▼

Mitigated through three strategies:

  1. Stable abstractions principle — Core contains only entities, VOs, and port interfaces (most stable parts). Volatile implementations live in engine packages.
  2. Narrow port interfaces — Each port scoped to single responsibility. A change to IHackDataPort affects only Hacks Engine — not Skills or Forensic.
  3. Turborepo dependency tracking — Automatic identification of affected packages on core changes. Immediate feedback if anything breaks.

In practice, core changes have been additive (new methods) rather than breaking. Stable because it contains only domain abstractions.

Q12 "How would you evolve this architecture for real-time exploit detection?" ▼

Three architectural changes, all accommodated by hexagonal architecture:

  1. New driving adapter — WebSocket/SSE adapter subscribing to on-chain events via Viem's watchEvent; pushes to SyncHacksUseCase in real-time
  2. Event-driven cross-engine communication — Redis Pub/Sub or BullMQ events so new HackIncident immediately triggers Forensic Engine trace analysis
  3. New IStreamPort — Port in @aegis/core for streaming domain events to frontend via WebSocket

None of these require modifying existing domain logic. SyncHacksUseCase doesn't care if data came from cron or real-time stream. This is the long-term payoff of hexagonal architecture — the domain core is protocol-agnostic.

Q13 "How do you academically validate that your AttackVector taxonomy is comprehensive?" ▼

Three-component validation approach:

  1. Empirical grounding — 16 categories derived from comprehensive survey of DeFiHackLabs, Rekt News, SlowMist. Each category requires ≥3 distinct historical incidents.
  2. Coverage analysis — Measure % of known exploits classifiable by our taxonomy. Target: ≥95% coverage.
  3. Inter-rater reliability — Multiple independent reviewers classify the same exploit set. Cohen's/Fleiss' kappa score above 0.8 validates well-defined categories.

Taxonomy is extensible — Zod enum can be expanded without breaking existing classifications.

Q14 "What are the scalability bottlenecks, and how would you address them?" ▼

Three primary considerations:

  1. Database queries — Addressed with PostgreSQL GIN indexes (JSONB), pg_trgm (text search), composite B-tree indexes on filtered columns.
  2. Foundry simulation concurrency — CPU/memory intensive. Horizontal scaling = worker pool (K8s jobs) with ISimulationPort routing to remote workers.
  3. ETL throughput — BullMQ natively supports concurrency, priorities, rate limiting. Horizontal = multiple worker instances on same Redis queue.

All scaling changes are adapter-level. Moving from local Foundry to remote cluster = new ISimulationPort adapter; SimulateExploitUseCase unchanged.

Q15 "If you had to start over, what would you do differently?" ▼
  1. Event sourcing for ETL — Every data change as an immutable event = complete audit trail + time-travel queries for academic reproducibility.
  2. Formal cross-engine event contract — Explicit domain events (HackIncidentCreated, SkillFileScanned, SimulationCompleted) from day one for cross-engine workflows.
  3. Evaluate GraphQL — Dashboard requires multiple API calls for one view. GraphQL could allow exact data requests in a single query.

Emphasis: these are optimizations, not fundamental flaws. Hexagonal architecture provides the right boundaries to introduce any of these incrementally without rewriting the domain core.

Q16 "How does your system handle the ethical implications of simulating real exploits?" ▼

Four key points:

  1. Not creating new exploits — Executing existing, publicly available Foundry POC tests from open-source repos like DeFiHackLabs.
  2. Forked mainnet state — Read-only copy at historical block number. No real funds at risk, no real transactions submitted.
  3. Industry standard — Responsible disclosure, red teaming, exploit reproduction are established methodologies in security research.
  4. Academic purpose — Thesis alignment section explicitly connects to structured research goals. Understanding attack methodologies through controlled simulation is essential for advancing Web3 security.
